# Design

## Context

现有后端镜像已经真实发布，仓库仍为 Private；没有 GitHub Release 或仓库 Secrets。工作流在默认分支修改时使用 Docker 编译服务端，安卓没有参与 CI。安卓及根 Gradle 版本均固定为 1.0.0，手机安装的是使用本机调试密钥签名的版本。设置页面已有后端连接、提醒授权和备份入口，没有更新入口。参见 proposal.md。

## Goals / Non-Goals

**Goals:** 标签驱动同版本交付，APK 与后端只编译一次；镜像实际使用公开 Release 中的后端包；手机直接检查、下载和发起覆盖更新，保留现有资料。

**Non-Goals:** 不自动部署后端，不引入账号密码、GitHub 登录或运行时 GitHub 凭据，不自动强制安装，不改变数据库结构或训练及提醒规则。

## Decisions

### 已确认决定

记录时间：2026-10-22 UTC+8。

1. **标签发布与产物复用**：用户原文“配置ci同步打包应用，release发布app和后端，然后构建镜像，构建复用release，ci流程要优化，通过tag控制release，app支持检查更新下载安装”。正式发布同时提供 APK 与后端运行包，再由该 Release 的后端包组装镜像。
2. **现有仓库公开**：用户在询问私有 Release 分发方式时回复“改成public吧”。将现有 `4o4E/personal-training` 改为 Public，Release 与源码公开，不另建发布仓库。此决定替代 `implement-personal-training-app/design.md` 已确认决定 8 及决定 9 中的仓库私有约束；其他范围与个人资料隔离要求继续有效。
3. **保持当前签名身份**：用户选择“沿用当前签名密钥”。固定已有密钥供正式构建使用，关闭 APK 调试功能，避免通过卸载重装转换签名。签名私钥保存在 CI Secrets 和仓库之外的安全位置。
4. **首个正式版本**：用户要求“发布一个新版本，版本号从0.0.1开始，触发构建app和镜像”。首个正式标签为 `v0.0.1`。

### 实施方式

- **统一版本来源**：正式标签采用 `vMAJOR.MINOR.PATCH`，从 `v0.0.1` 开始。Gradle 接受一次传入的版本，应用与后端共用该值；安卓内部版本号按 `MAJOR × 1000000 + MINOR × 1000 + PATCH + 1` 生成，次版本与修订号限定为 0–999，符合平台上限。偏移一位确保 v0.0.1 的内部版本号为 2，能够覆盖既有内部版本号为 1 的手机安装。拒绝不符合规则的正式标签。
- **普通检查与正式交付分开**：普通提交及拉取请求检查受影响工程，不发布。正式标签工作流使用一个 Gradle 执行图完成 `:server:test`、`:server:distZip` 和 `:android:assembleRelease`；复用共享模块构建，使用 Gradle 缓存和现有并行配置，不启动安卓模拟器。
- **Release 先于镜像**：构建成功后在同一仓库发布签名 APK、含依赖与动作素材的后端 ZIP、`update.json`。更新资料包含版本、内部版本号、APK 附件名、字节数、SHA-256 和面向用户的更新说明。公开 Release 成为部署与手机更新的共同来源。
- **Docker 只组装运行环境**：镜像任务下载当前标签的 Release 后端 ZIP，展开并按框架依赖、动作素材、应用代码准备三个目录；Dockerfile 仅使用 JRE 和这些产物，不再包含 JDK、源码或 Gradle。容器启动与鉴权检查通过后推送版本标签与 latest，继续匿名拉取验收。镜像发布失败时 CI 明确失败，不将既有 latest 标为已更新。
- **权限与发布顺序**：签名仅用于正式标签任务；Release 发布使用本仓库的 GITHUB_TOKEN，镜像任务拥有 packages 写入权限。发布任务不因后续提交自动取消，避免中途终止正式交付；普通检查允许取消过时运行。不同版本按顺序发布，不自动替换已有版本附件。
- **更新逻辑集中**：新增安卓更新实现，封装公开 Release 查询、版本判定、下载状态和安装调用，设置页面只展示状态和操作。不经训练后端，不把业务 token 加入 GitHub 请求。
- **采用系统下载能力**：使用 DownloadManager 保存 APK 到应用专属目录，展示真实字节进度；下载任务和必要的版本资料保存在本地独立设置中，不改变训练数据库。离开设置页面不终止系统下载，重新打开可以恢复查看。
- **验证后交给系统安装**：验证下载大小和 SHA-256，读取包名、内部版本号与签名身份，只有与所选发布一致的 APK 才进入安装。使用 FileProvider 授予系统临时读取权限；通过系统安装界面让用户确认。缺少安装来源授权时打开对应设置，返回后可继续安装，不请求共享存储权限。
- **中文且不干扰训练**：更新入口显示当前版本、最新状态、用户可读的更新说明、进度和失败原因；不自动打断正在进行的训练，不自动下载或强制安装。检查失败不显示为已是最新版本。

以上为依据现有工程与平台能力选择的实施方式，不增加需要用户选择的业务规则。独立公开仓库及私有 Release 代理方案因用户已选择公开现有仓库而不采用。

## Risks / Trade-offs

- [公开源码可能被第三方复制] → 执行公开前检查实际已跟踪文件、现有发布与日志，不上传个人资料及凭据；公开后不能保证撤回第三方已复制内容。
- [固定签名密钥丢失会影响覆盖更新] → 核实当前 APK 和密钥的签名身份一致，安全保存密钥及 CI Secrets，不记录密钥内容或密码。
- [系统安装需要用户交互] → 明确提供授权和确认步骤，不承诺普通应用静默安装。
- [GitHub 下载受网络条件影响] → 如实显示检查或下载失败，允许用户再次操作；不影响离线训练，不增加自建下载镜像或后台重试策略。
- [Release 已发布但后续镜像步骤失败] → 保留可追溯的已检查 Release，CI 明确失败；镜像任务重新使用同一份 Release 产物完成发布，不重新编译或覆盖附件。

## Migration Plan

1. 检查实际跟踪内容及已安装签名，配置受保护的既有签名密钥；将现有仓库改为 Public，更新当前部署说明及旧决定的替代标记。
2. 替换现有发布流程和 Docker 构建方式，加入版本定义与更新资料；实现中文更新入口及安卓下载和安装能力。
3. 本机构建并在手机覆盖安装具备更新能力的版本，保留原有资料；使用正式标签执行真实 CI，匿名取得 APK、后端包和镜像，实际运行后端包及容器检查。
4. 手机从真实公开 Release 检查、下载并通过系统安装升级到更高版本，确认版本及训练资料保留；部署仍由用户自行执行 Compose。
5. 后端需要退回时由用户选择既有版本镜像；应用不自动降级，签名和资料继续保留。
