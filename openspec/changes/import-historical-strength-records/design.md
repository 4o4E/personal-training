# Design

## Context

动机和范围见 `proposal.md`，行为要求见 `specs/historical-strength-records/spec.md`。

已检查现有实现：

- `shared/Domain.kt` 的 `Session` 强制具有 `snapshot`、`startedAt`，`SetResult` 强制具有 `completedAt`，每组只有单一 `load`。完成状态还要求有 `endedAt`，实际组索引必须对应目标组。
- `summarizeHistory` 按 `startedAt` 排序；后端 `Main.kt` 的 `/v1/history` 用毫秒时间筛选；Android `HistoryScreen` / `SessionHistory` 直接显示开始时间和原计划。直接使用零点、18:00或导入时间都会把未知信息伪装成真实时间。
- `TrainingViewModel.newPlanItem` 读取实际组时间选择历史负重，`TrainingPresets.rotationPlans` 和 `nextSlot` 读取开始时计划。共享格式调整必须覆盖这些消费者，不只修改导入端。
- 后端 `Store` 与 Android Room 均将业务内容保存为 JSON。扩展 JSON 不需要增加 SQLite 表或 Room 列，保留现有表结构与 Room version 1；本设计不执行数据库 DDL。
- 后端 `Store.import` 已整包核验并在事务内合并，相同内容不重复保存，冲突可停止；共享 `BackupIO` 与后端目前只接受备份版本1。
- 已用实际 token 只读访问 `https://training.e404.top:3443/`：健康及鉴权均成功，具有439个动作、442份素材、20个部位和一个分化方案，没有实际训练。此信息是规划时观察，不替代导入前重新读取。
- 当前 Ubuntu 入口 `auditro` 为只读，不能由本任务擅自升级权限、重启或部署容器。生产更新沿既有用户部署流程执行，实际导入走已授权的业务接口。

## Goals / Non-Goals

**Goals:**

- 在共享领域格式中真实表达“时间或当时计划未记录”，让手机、后端、skill 和备份读取相同含义。
- 为本批已知来源提供可核对、可重复且不覆盖既有资料的导入；不为导入创建助手专用数据库接口。
- 在更新软件后继续执行正常训练；历史记录不触发计时、不绑定推断的实际器械、不修改现有轮换。

**Non-Goals:**

- 不增加羽毛球或其他按运动时长记录的类型，不采集小米、Hevy或其他应用数据。
- 不编写任意 Markdown 的通用解析器，不改写八个原始文件，不增加训练目标、器械身份或恢复判断。
- 不新增实时训练的降重组编排界面，不改动通知策略、导航、候选方案和深色模式。

## Decisions

### 已确认决定及确认原文

1. 用户请求：“把已有数据导入当前运行的后端”。目标沿用已经连接成功的个人生产后端。
2. 用户在“是否允许先补齐历史记录支持，再执行导入”的确认中选择：“仅导入八次力量训练”。该选项说明为：“只补齐历史日期和组内降重支持；更新应用及后端后，导入98个记录组与反馈。羽毛球保留在原文件，不纳入本次导入。”
3. 以实际完成内容为准、保留原始单位与反馈、导入前备份、合并且不覆盖，以及不改写原始记录，均已在此次确认的操作方案中说明。

### 助手建议：以明确缺失值扩展既有训练记录

继续使用 `Kind.session` 与现有 `/v1` 接口。在 `Session` 增加可选历史来源资料，包含稳定来源标识、UTC+8 本地日期和原始全文；该资料存在时表示从已有记录整理的已结束训练，而不是实时训练。具体类型与字段名在实施时沿既有命名规范确定。

- 实时训练仍必须有开始时计划、真实开始时间和每组完成时间，结束时保存真实结束时间；现有计时约束保持。
- 本批历史记录缺少的 `startedAt`、`endedAt`、`completedAt` 与 `snapshot` 允许为空；历史来源及日期明确存在，状态为已完成且有实际完成组。不用无意义的占位计划或虚构时间满足旧约束。
- 复用实际执行条目保存动作顺序，目标组保持为空；实际组用自己的条目标识与组索引关联。仅历史模式不要求实际组索引对应不存在的目标组；实时训练继续核验目标。页面不显示“当时计划”或“计划组数”，而显示实际组及“原始计划未记录”。
- 近似开始时间保留在原文与说明中，不转为精确时间。来源资料与原始日期在创建后保持不可被普通历史编辑改写。

选择扩展同一训练记录，而不是增加另一套历史文档种类，是为了让同步、鉴权、历史查询、删除和备份继续通过现有入口处理。新增 nullable 状态表示真实缺失信息，并非错误时的替代值；共享规则必须区分历史与实时两种真实来源。

### 助手建议：在实际组中加入有序分段

给 `SetResult` 增加默认空列表的分段明细，每段包含实际次数和原始负重。普通组继续使用现有次数与单一负重；本次降重组保存两段，并保留可核验的总次数10，不设置一个冒充全组负重的汇总重量。

共享规则核验分段总次数与整组次数一致，统计仍按实际组记录计数，不按分段条数计数。历史详情优先展示各段；API、备份与 skill 不将其压平成一种重量。实时训练的普通录入不增加新的选择或编辑流程。

### 助手建议：未明确的负重含义使用未知状态

明确写明“左右各”的记录采用单侧配重，保持原始数字，不增加杠铃或器械自重。没有明确总重量、单只或单侧含义的读数仍保留数值和单位，在 `Load.meaning` 增加未知含义值并显示“重量含义未记录”，而不是利用现有默认值猜测总重量。

该状态仅表达已有资料缺失的事实，不新增器械配置选择或自动换算。动作名称足够明确时复用现有动作；具体形式不足以确认时保留原始动作名称作为历史动作资料，不绑定近似器械、不提供冒充已确认形式的教学，不创建推断的健身房和器械。对于没有真实器械身份的本批历史，不把相同动作名称作为自动复用负重或同器械进步比较的依据。

### 助手建议：共享日期语义，不创建假时间

共享历史日期提取与比较规则：历史记录使用保存的本地日期，实时训练从真实开始时间转换为 UTC+8 日期。按日期筛选包含两端；同日只有实际知道时间的记录才比较时间，未知的同日顺序以稳定标识确定，不声明真实先后。

手机记录列表、后端范围查询与相关历史消费者复用此规则，不将本地日期转换为假装真实的毫秒时间。由于本批没有原始分化方案绑定，导入后不推进现有分化；保持实时训练的 `nextSlot` 行为。

### 助手建议：版本化备份与一次明确的软件更新

新版本统一导出格式版本2，读入版本1和2；已有版本1记录通过相同领域解码保留原有时间和计划，不提供旧接口别名或第二套业务实现。旧软件目前已明确拒绝非版本1的数据包，因此版本2可以阻止旧导入流程静默丢失分段等新增资料。

新应用须能读取旧后端的正常资料，再完成生产后端更新，最后导入历史记录。保留既有包名、签名与唯一 token。旧0.0.2不能读取本次含空时间和空原计划的新记录，不能在导入后继续使用旧客户端；升级顺序是必要条件，不设计虚构时间的兼容格式。

### 助手建议：确定来源转换为完整合并数据包

转换过程只处理八个明确文件，以固定来源标识构造稳定的训练、条目与必要动作标识，使用版本2完整数据包，通过现有 `POST /v1/import?replace=false` 导入。转换资料保留原文以追溯近似时间、未知器械及次日反馈；结构化结果只反映真实完成。

复用既有目录不复制全量动作与素材；新增的历史动作与训练一起进行关联核验和事务合并。源文件、既有分化方案、计划与器械资料不改写。实际备份和导入包不进入 Git、不含 token；导入成功后按工作区规则确认保留位置或删除转换临时资料。

### 用户确认：发布与生产导入

用户要求将八次真实训练记录导入后端，明确手机现有数据是测试数据，并确认通过既有流程发布v0.0.3正式应用、后端运行包及镜像。应用安装与生产Compose部署由用户完成，实际验证更新条件后才执行生产导入；手机测试数据不作为本批来源，只读基础设施权限不改变。

## Risks / Trade-offs

- [旧客户端无法解码新记录] → 先验证新版应用可保留旧数据并读取旧后端，完成应用与后端更新后才写入历史；备份升级为版本2。
- [现有消费者把缺失时间或计划当成编程错误] → 实施时查询共享导出符号的全部引用，更新历史查询、展示、轮换与负重参考；实时训练仍用强约束保证必要信息。
- [目标组与实际结果被混淆] → 历史记录原计划缺失、目标组为空，只从真实结果统计98组，详情不宣称复制出来的目标是当时计划。
- [模糊动作名称或重量含义引入错误分析] → 保留原文与未知状态，不猜测实际器械，不把未知含义读数纳入跨器械比较。
- [导入前服务器已被手机改写] → 正式导入前重新读取并导出完整备份，合并事务核验同标识资料，冲突立即停止；不使用 replace。
- [导入后回退旧程序导致资料不可读] → 有新记录的数据库不能直接配旧程序。回退以导入前备份为依据，必须先取得用户确认，并处理其后新增的真实手机记录，不擅自恢复数据库或删除记录。

## Migration Plan

1. 在独立真实 SQLite 后端验证仅日期记录、单组两段重量、日期筛选、旧资料兼容、事务冲突与备份往返；核对本批八日共98组，并实际运行项目级 CLI。
2. 在独立 Android 验证包确认历史列表与详情、原始反馈、分段显示、深色模式及正常完成组和组间通知；验证正常升级保留连接与原数据，不覆盖正式手机数据进行试验。
3. 通过既有标签发布流程构建同版应用、后端和镜像；应用沿既有正式签名更新，不建立第二套发布方式。
4. 用户安装新版正式应用并沿既有 Compose 流程更新生产后端；助手使用授权只读入口及业务接口核对运行版本和连接，不绕过基础设施权限。
5. 重新读取生产资料，导出完整备份；按同一套业务接口执行合并导入，不直接打开生产 SQLite 写入。
6. 读取全部八次记录逐日核对组数、实际重量、两段降重及原文反馈；再次提交相同资料验证无重复，按日期查询核对统计。确认没有羽毛球记录、现有方案和计划没有改写。
7. 手机同步并实际查看日期与降重组；报告实际导入结果、备份位置与验证证据。遇到冲突或更新条件不满足时停止写入，明确给出所需用户操作。
