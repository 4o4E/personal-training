# Design

## Context

历史训练使用与实时训练相同的Session、动作、执行条目与SetResult；后端SQLite和Android Room均保存业务JSON。本次调整只修改JSON业务格式与展示，不修改SQLite表、Room列或Room版本。

生产已有八次历史训练、98组，正式应用和后端为0.0.3。原始Markdown位于record/，不是应用的数据格式。生产基础设施入口auditro只读，部署由用户执行，记录更新使用现有鉴权业务接口。

## Goals / Non-Goals

**Goals:** 日历展示训练分类与实际组数；原生记录保留真实日期、动作顺序、原始单位、降重分段和整理后的反馈；工作区保存原始资料，云端不保存Markdown全文。修改现有八条记录而非重复导入。

**Non-Goals:** 不实现通用Markdown解析器，不迁移羽毛球或小米资料，不推断精确时间、实际器械或未知负重含义，不改变训练推荐、轮换或通知行为。

## Decisions

### 用户确认的行为

- 已确认仅整理10月12、13、14、15、19、20、21、26日八次力量训练，实际组数分别为8、7、10、15、13、15、15、15，共98组。
- 用户要求日历显示推拉腿等明确选择及完成组数，不显示长记录名称、记录条数和来源说明。
- 用户要求导入采用应用格式，而不是保存Markdown；确认原生记录与反馈整理方案后要求开始。
- 用户明确：没有明确的三分化时标记为“自由锻炼”。10月12日为自由锻炼，其余已确认类别依次为拉、腿、推、拉、腿、推、拉。四、五及其他N分化仍使用其明确选择的名称。
- 原始记录文件、真实完成量、原始单位、既有方案与器械资料保持不变；修改生产前重新备份，版本冲突停止，不全量覆盖。

### 训练分类独立保存

Session增加可空splitSlotName，保存开始时明确选择的SplitSlot.name，不通过之后可变的计划或方案反推历史。没有明确分类时为空；历史整理可保存已确认的短标签，不因此绑定当前分化或伪造原计划。

共享sessionTrainingLabel提供展示名称：标准推、拉、腿名称简写为推、拉、腿；其他明确分化名称保留；缺失时显示自由锻炼。Session.name继续表达训练名称，不用于推断分类。

日历每格仅包含日期、分类及实际完成组数，同日多次训练合计实际结果并表达不同分类，点击进入全部详情。组数来自SetResult，计划目标不计入，单组的多个分段不分别计组。同步状态保留在页面级位置。格子高度统一，较长分类至多两行，月份切换与日期滚动保持可用。

### 历史资料使用原生字段

HistoricalSource仅保留sourceId与UTC+8的localDate；移除originalText。动作、实际条目与各组内容继续使用同一原生模型。Session.notes只保存本批整理后的普通反馈文字，包含真实行内反馈、次日反馈、近似时间及下次调整说明，不复制原始计划表或Markdown全文。

原始Markdown留在工作区。没有精确开始、结束、每组完成时间及原始计划时保留null；目标组仍为空，不使用实际结果反造目标。来源标识用于追溯和避免重复，不作为另一套记录正文。

### 负重与分段

Load保留原始kg/lb及已明确的单只、单侧、总重量或助力含义。unknown仍为数据中的未知状态，界面仅显示数值和单位，不显示“重量含义未记录”，也不猜测含义。

SetResult的有序segments保留每段负重和次数，分段总次数与整组次数一致，只统计一个组。10月13日的10kg×4次与7.5kg×6次仍为一组，当天共7组。

### 备份和更新顺序

新导出使用版本3，读入版本1、2、3。旧备份读取时移除已经废弃的历史原文字段，其他原生资料与用户备注保持；不加入通用Markdown解释逻辑。旧库存及手机缓存的文档读取仅对历史来源字段作相同投影，不直接改写数据库；导出也投影为版本3。新文档写入和版本3备份导入不接受已废弃的原文字段，避免旧客户端重新写入。

新客户端能够读取现有0.0.3资料。由于旧客户端要求历史原文字段，先更新正式客户端与后端，再整理生产八条记录；旧客户端不得继续写入新格式。保留包名、签名、唯一token与既有发布流程，不修改基础设施权限。

### 已有八条记录的受控整理

一次性脚本读取最新完整备份和八个已确认来源，生成既有同步接口的mutation，baseRevision来自实际备份。只改变name、splitSlotName、notes以及移除historicalSource.originalText；自由锻炼分类为空，其余为已确认短标签。已有id、时间、items、exercises、results、原始重量单位和分段逐项保持。

主助手在独立真实后端验证后，重新读取生产并完整备份，再提交八条带修订号的更新。发生冲突即停止，不删除重建，不使用全量replace覆盖其他资料。记录和素材备份不含凭据、不进入Git。

## Risks / Trade-offs

- 旧客户端不能解码原文字段已移除的记录：应用与后端先更新，再整理生产数据。
- 根据当前方案或动作组合推断旧分类会篡改含义：只保存已选择或已确认的分类，否则自由锻炼。
- 以kg/lb推断单只或总重量会改变数据：保留未知状态，只调整显示。
- 整理备注时混入计划目标：逐日仅保留实际反馈，原生组结果保持逐项相同。
- 备份之后产生并发编辑：使用已有修订号冲突机制，停止并报告，不覆盖新内容。

## Migration Plan

1. 更新共享格式、既有备份读取与业务校验，迁移全部调用及接口、skill说明。
2. 更新训练开始时分类保存、日历摘要和原生详情，验证自由锻炼、明确分化、同日多次和实际组数。
3. 从真实备份整理八条更新，在独立SQLite后端核对98组、反馈、旧备份、新备份往返及修订号冲突。
4. 主助手统一构建并在独立Android应用验收；按既有流程准备同版正式应用和后端。
5. 正式应用及生产后端更新后，重新备份并更新现有八条；核对所有实际组不变、其他文档与素材不变，手机同步显示正确。
6. 保留用户要求的生产备份，临时资料按用户确认清理；不自动归档其他变更。
