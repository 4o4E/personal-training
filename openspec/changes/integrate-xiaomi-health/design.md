# Design

## Context

动机与交付范围见proposal.md。现有应用使用Compose、Room与Ktor/SQLite，普通业务保存在通用documents中，手机启动将这些文档载入内存。健康分钟数据不能逐条加入这条同步通道。

2026-10-28只读核对：生产导出为formatVersion=4，现有本地应用为每日唯一训练格式5；健康检查与空mutation同步均返回200。生产10月27日已有16组，当前连接的一加9R正式应用仍为0.0.4，不能代替用户刚更新手机的故障证据。首次健康源有36条运动摘要、18条体成分、475段睡眠和190273条日常心率；源库约34MB。

当前主规范尚未同步。既有业务要求来自focus-training-workflow及release-training-app-updates，本变更沿用其能力路径；归入主规范时先同步基线，再应用本变更，不能因主规范目录为空建立第二套同义能力。

## Goals / Non-Goals

**Goals:** 将采集、健康存储与读取、训练文档同步分开；共享真实数据格式与来源规则，使手机和助手通过同一接口得到一致内容。健康刷新不阻塞训练，失败不丢失待上传内容。

**Non-Goals:** 不重写misports脚本，不把运动摘要当作力量训练，不提供本次范围以外的运动秒级曲线或GPS地图，不增加底部导航、账号体系、iOS或浏览器客户端，不改变计时通知行为。

## Decisions

### 已确认决定

记录日期：2026-10-28。确认来源为本轮用户需求和选择问题的回答。

1. 用户反馈：“昨天的数据显示待同步，或者以前的数据显示本机保存副本，同步失败”；同步信息“只应该放在一个地方……运动记录的顶部……要有重试按钮”。统一展示位置与明确失败阶段是需求，不将所有历史的存储状态等同于一次网络尝试。
2. 用户要求拉与腿高亮可区分，接入当前工作区小米健康，且自由运动可记录开始结束。当前术语中的独立自定义运动承载羽毛球、徒步等内容；已有自由力量训练继续使用Session，不引入第二种力量记录。
3. 用户选择“全部完成后统一发布”，不先单独发布修复版。应用、后端、采集器及健康接入全部就绪后统一交付。
4. 用户选择“服务器自动采集”，接受独立采集容器、电脑关机不影响采集、服务器持久保存轮换凭据及单一自动采集端。
5. 对“是否同意新增后端健康数据表和手机离线缓存，并按以下哪种范围接入”，用户选择“日常健康与运动摘要”。此项授权后端和Room的必要schema迁移；范围包含日常指标和运动摘要，排除运动秒级样本与GPS接入，原来源保持不变。

以下为实现设计，不将具体字段、接口路径、调度周期或库选择写成用户指定。

### 1. 同步卡与兼容检查

移除MainActivity共享页面容器中的同步横幅、SettingsScreen的重复状态及历史详情逐条同步文字。运动记录顶部使用一个同步卡，训练记录和健康内容共用；设置保留地址/token保存及断开操作。冲突从同步卡进入现有选择逻辑，显示真实待上传数量及训练、素材、健康下载、小米采集各阶段结果。

训练资料的成功时间在后端确认并写入本机事务后更新，与素材下载结果分开。素材或健康错误不能把已确认训练改成未上传。重试使用现有同步互斥，不生成第二套训练上传队列；进行中禁用重复点击。小米采集的重试向后端发出采集请求，不能只下载旧健康数据。

新增受现有token保护的`GET /v1/capabilities`，提供应用发布版本、业务/备份格式及健康接口版本。本次业务格式为6，健康接口版本为1。客户端和采集器在写入前检查契约；旧端没有能力接口或格式不匹配时，明确提示应升级哪一端，停止不兼容写入，保留离线训练。普通网络、鉴权或服务错误保持其真实原因，不都归类为版本问题。此检查不提供丢字段或忽略错误的兼容路径。

### 2. 健康领域与存储

在shared增加明确类型的健康记录与传输对象，数据集为steps、calories、heartRate、restingHeartRate、sleep、body、activity。源秒数在采集提交边界一次性转为epoch毫秒；接口时间统一毫秒，业务日期统一UTC+8，睡眠按起床日期、运动按开始日期。保留原单位和可空字段，体成分及运动摘要覆盖源库现有可用量值，不凭字段名猜测换算。

后端在现有应用SQLite中新增健康专用表，不往普通documents逐条塞入采样：

- `health_records`：dataset、source_id、local_date、measured_at、payload，主键(dataset, source_id)，按dataset/date/time建立查询索引。payload是经过共享类型校验的结构化记录，不是任意原始响应；睡眠记录内包含分期，运动摘要不含采样或轨迹。
- `health_days`：local_date、revision，用于已变化日期的读取和缓存更新。
- `health_collection_state`：单一采集端的待执行请求、当前阶段、最近开始/成功、失败原因及提交状态。

此选择复用当前“固定索引字段加结构化JSON”的存储方式，避免为每个体成分指标建立多余接口，又将健康数据从普通文档全量读取和冲突流中分离。健康SQL操作封装在HealthStore，由现有Store协调同一连接、事务与运动文档更新，不建立第二个无协调写入者。按天统计仅查询所需数据集或提取相关量值，不在每次请求解码整份历史。

来源键保留现有自然身份：分钟以类型和来源分钟确定，心率包含采样类型，体成分/睡眠/运动采用原source_id。重复提交相同数据不产生重复记录或无意义的新日期修订。源的空响应不是删除指令；完整备份的明确替换另走导入规则。

### 3. 接口与缓存契约

所有业务接口沿用现有唯一token，`/health`仍仅用于服务存活检查。

|接口|行为|
|---|---|
|`GET /v1/capabilities`|声明配套格式与健康接口能力|
|`POST /v1/health/import`|按数据集分批提交规范化记录，以自然键幂等更新；返回实际接收结果，不返回伪造成功|
|`GET /v1/health/status`|已覆盖日期、健康修订及采集阶段/最近成功/失败原因|
|`GET /v1/health/days?from=&to=`|读取有限日期范围的日汇总及日期修订|
|`GET /v1/health/records?date=&dataset=&cursor=`|按一个日期和数据集读取确定顺序的记录，返回日期修订、固定有界页大小和续页游标；不在一次响应返回全部历史|
|`POST /v1/health/collection/request`|请求一次服务器采集，已有请求或任务进行中时合并请求|
|`POST /v1/health/collection/state`|采集器报告开始、提交、成功或失败，失败不推进成功时间|

服务器完整备份仍通过现有导出/导入入口。项目级skill调用相同健康接口，不直连源数据库，不另建绕过鉴权的助手接口。

Room升版增加独立健康汇总/详情缓存与其修订、读取时间；汇总覆盖和详情覆盖分开记录，详情完整性至少按日期、数据集、来源修订区分，只有同一修订的全部分页读取完成才标记该数据集完整。其他数据集或尚未取完的分页不能因已有日汇总而标为已下载。分页期间来源修订改变时重新读取该范围，不将混合修订标为完整，原缓存仍可查看。不把健康行加入现有documents缓存。手机先展示缓存，再刷新所选范围；成功结果覆盖对应缓存，失败不清空。健康下载由独立读取流程处理，不占用训练计时，也不在启动同步中等待全部历史样本。重复页按来源键归并；未下载不能显示为无记录。版本迁移保留已有documents、dirty、conflict、计时和设置，不采用破坏性重建。

### 4. 运动摘要、自定义起止与既有编辑

ActivityRecord增加可空startedAt、endedAt，并保留durationSeconds等既有字段。表单使用日期与时间控件，不要求手输时间文本；新建记录有完整起止且未单独填写时长时可计算默认记录时长，已有或来源给出的时长不被时间差自动覆盖。未知端点保持null，已知结束不得早于开始，跨日记录按开始日归档。详情显示时分区间，跨日时附必要日期信息，避免把不同日期误看成倒置。

小米运动摘要只保存在健康表，作为健康详情中的只读来源事实；不创建或更新用户 `activity` 文档，不以采集结果覆盖已有活动。活动日历只显示用户明确手动录入或明确导入的记录。旧自动投影须以专用服务端 `id=xiaomi-…` 且 `sourceId=misports:activities:…` 双重条件识别后退出日历及用户运动列表；不能仅按sourceId前缀过滤，因为明确导入徒步 `activity-misports-20261017-walking` 的来源也以`misports:`开头。手动UUID和明确导入ID均保留。健康原始摘要及已存数据不删除或改写；本轮不改变schema、业务格式或数据格式。

### 5. 健康界面与分类颜色

运动记录保留顶部唯一同步卡，内部切换“训练记录”和“健康数据”。日历的连续周行、今天底色、相同边框宽度、64dp容器及未来预览不改变；推绿色、拉蓝色、腿橙色、自由灰色，不再借用错误状态颜色作为腿日颜色，深浅模式分别确定可读值。

健康内容按日期展示概览，并可查看真实心率采样、睡眠段与分期、当日测量及全部可用体成分量值。主睡眠取最长一段并标明口径，其他睡眠不擅自称午睡；同日多次体成分都保留。最近测量明确显示真实日期，缺失不填零。小米运动摘要仅在健康详情只读展示，不进入训练日历或用户活动列表，也不自动创建或更新用户活动；步数等日常指标不生成训练标记，健康数据不消费分化。

### 6. 服务器采集器

新增独立Python运行模块，直接复用`misports/milib`、schema和依赖，不修改原CLI或同步实现。构建通过明确源码白名单打包这些文件，不在源码树维护第二份采集库，也不把使用指南中的私人资料或data目录打包。

服务器持久化目录保存采集SQLite、原始响应、轮换凭据及后端提交进度；程序目录只读。首次使用工作区SQLite的一致性副本作为种子，先发布确认范围内的全部历史，再进入服务器持续更新。原库与现有样本/GPS保留，本次服务器任务按选定范围使用`include_fds=False`，不改变原CLI的完整采集能力。

采用成熟调度器的串行任务：默认每小时执行，启动补执行一次；轻量检查后端待执行请求以响应手机重试，不开放额外公网端口。同一时间仅一个采集任务持有凭据。账号登录后立即保存轮换结果，不等全部采集完成；迁移完成后电脑不再运行自动采集。

现有`sync()`会把数据集错误记到本轮meta.json但仍返回计数，运行模块必须定位本轮结果并检查errors，不能只看退出码或打印文字。必需数据集失败时报告并终止本轮健康提交，不伪装成功；正常下次调度或用户请求可重新执行。异常在任务边界记录阶段后继续抛出，不提供假数据或静默回退。

初次全量提交与后续增量采用相同接口。提交进度单独持久化，成功批次确认后才前移；从来源水位重叠读取，覆盖既有采集器的一天回看，保留显式历史重扫命令。体成分、睡眠及运动按来源键更新，分钟数据沿用采集端已去重的事实，不再次猜测去重或改写源库。

### 7. 备份、发布与开放操作

业务/备份格式升为6。后端完整ZIP在既有data.json与media之外增加健康清单及分流记录，流式导出，不将几十万健康行塞进data.json。健康清单声明完整或缓存范围；完整导入先校验全部内容，再事务性写入训练、活动关联及健康资料；默认合并遇到不同内容继续要求明确处理，不以缺失内容当作删除。版本1至5的训练包继续通过现有迁移读取。

手机保留原训练备份的离线导入导出，本机导出明确为“本机资料，健康仅含已下载内容”。在线提供后端完整备份取得与恢复；包含完整健康记录的包通过后端导入，离线时明确拒绝且不先修改部分训练资料，不新增复杂的离线健康恢复队列。只读健康缓存可重新下载，但不能将它描述为全部健康资料。

当前最新正式版本为v0.0.5，本次目标为v0.0.6及对应递增内部版本。同一tag产生APK、后端ZIP、采集器ZIP、更新清单；后端和采集器镜像分别从实际Release包组装并使用latest。CI覆盖采集源码与包装模块的路径，复用已有Gradle及镜像缓存，不在镜像阶段重复编译。采集器镜像不包含真实种子数据库或凭据。

Compose沿用现有后端服务，增加独立采集服务和私有持久化目录；采集器通过内部服务地址访问同一后端鉴权接口。部署端另行放入源数据库副本与小米凭据，不在公开Compose示例填写真实值。API说明及项目级skill增加健康查询、提交、状态、重试和完整备份操作。

## Risks / Trade-offs

- 前后端格式不一致 → 发布门槛包含旧格式升级与真实同步；运行时检查能力并保留未上传数据，不能用同名APK掩盖契约差异。
- 海量采样挤占训练同步 → 独立健康表、日期范围、分页及缓存，不加入普通documents和训练同步的全量内存。
- 小米凭据轮换或过期 → 单一采集者持久保存；失效明确报错，需重新授权时说明实际缺失，不把旧数据当新结果。
- [来源摘要更新被误读或触发用户活动写入] → 小米运动摘要仅作为只读健康事实保存和查看，自动采集不得创建或更新用户活动；既有手动和明确导入活动保持独立，健康来源资料不删除或改写。
- 手机只缓存部分健康数据 → 导出名称与健康清单明确范围，完整恢复由在线后端完成，训练离线能力保持。
- 服务器只读权限边界 → 当前auditro不能部署；提供明确Compose和私有资料配置，由用户执行生产更新后再验证，不尝试绕过权限。

## Migration Plan

1. 明确共享契约和文件所有者，后端、采集器、Android数据与界面、发布配置按真实依赖并行实施；消费者使用同一份已定义契约，不各自扩展格式。使用独立后端和一加9R验证应用，正式资料不作为开发写入目标。
2. 对现有生产v4备份在独立环境升级，验证每天一份训练、原单位、历史未知时间、离线待上传以及完整备份恢复。核对现有小米库全量接入、再次提交、源徒步关联及健康缓存。
3. 全部功能及真实路径通过后统一创建v0.0.6标签。验证签名、更新清单、公开Release、两个镜像与匿名拉取，不能以本机构建代替正式CI结果。
4. 生产操作前导出后端及正在使用的手机资料；由用户升级后端和采集器并配置私有种子与凭据。先核对后端能力与原训练，再接入健康，最后覆盖安装配套APK。
5. 实际手机重试同步，核对10月27日原16组及其待上传修改、其他历史和健康内容；当前一加9R的旧正式应用不能替代该验收。生产更新及实际手机未具备时，该验收保持未完成。
6. 需要回退时停止新写入并恢复升级前完整后端及对应手机备份，同时恢复匹配版本；不能仅把旧镜像接到已经升级的新库上。
