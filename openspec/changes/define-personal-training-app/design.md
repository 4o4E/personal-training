# Design

## Context

动机参见 `proposal.md`。当前工作区保存运动记录和小米运动数据采集工具，尚无本应用实现。本文记录已经确认的选择、选择依据和实施前仍需确认的事项；不把规范文件齐备解释为应用可以立即进入全部实施。

记录时间：2026-10-21 17:44:17 UTC+8。以下已确认决定当前有效，应用功能尚未实现。引用原文的内容来自用户消息；没有原文引号的条目是此前确认内容的转述，不补写用户未说明的理由。

## Goals / Non-Goals

**Goals:**

- 保留用户已经作出的产品和架构选择，为后续实施提供约束。
- 将训练计划、实际记录、器械读数及动作素材的含义分开，避免后续更换动作或素材时破坏历史。
- 用相同业务接口服务原生应用和助手，未来网页只读取同一份资料。

**Non-Goals:**

- 本次不实现安卓应用、后端、数据迁移、通知原型或操作 skill，不声明这些功能已可使用。
- 不代替用户决定未确认的后端、数据库和同步策略，不未经确认执行数据库 schema 变更。
- 不创建第二套架构决定记录；`.workspace/ADR.md` 仅作为本文入口。

## Decisions

### D01：单人私用与平台范围

- 状态：已确认。
- 决定：只供本人使用，安卓最优先，不考虑 iOS；不以分发和合规准备作为当前任务。
- 确认依据：“项目只有我用，合规问题无须考虑”“安卓是最重要的”“不需要考虑ios”。
- 用户给出的理由：个人使用，不是分发项目。
- 适用规范：`project-workflow`、`android-training-runtime`。

### D02：原生安卓客户端

- 状态：已确认。
- 决定：采用原生 Kotlin + Jetpack Compose。未来浏览器只做数据浏览，不建立第二套训练流程。
- 确认依据：此前技术选型讨论已确认原生 Kotlin + Jetpack Compose，以及浏览器只读边界；用户要求“希望少维护平台代码”。
- 用户给出的理由：原生通知稳定、安卓优先，避免维护其他不需要的平台。
- 已讨论的路线：网页不承担原生训练提醒；跨平台路线不作为已经选定的实现。
- 适用规范：`android-training-runtime`、`read-only-web`。具体框架选择属于本文的实现约束，不写入动作业务规范。

### D03：原生定时提醒为最高优先级

- 状态：已确认。
- 决定：原生通知和定时唤醒能力优先保障；完成一组后进入组间休息，到时提醒用户。
- 确认依据：“应用才能稳定原生通知”“要支持定时唤醒之类的功能，并且是最高优先级的支持”“练完了点一下完成一组进入组间休息”；2026-10-22 追加确认“不需要处理极端场景”“不要用系统的闹钟响铃”“只要唤醒自己然后发通知提示”。
- 用户给出的理由：减少手动计算组间休息，保持应用后台使用时的提醒能力。
- 技术边界：到时唤醒应用并发送普通通知，提示音和振动遵循系统通知设置；不注册用户可见的系统闹钟，不使用闹钟铃声或全屏界面。验证日常训练、切换应用和息屏，不扩展极端场景。
- 适用规范：`android-training-runtime`。

### D04：以 N 分化和训练部位组织计划

- 状态：已确认。
- 决定：先选择 N 分化方式并配置训练部位，动作可以灵活替换，训练前能够预览未来几天安排。
- 确认依据：“选择n分化的训练方式，然后配置要训练的部位”“可以灵活切换动作”“可以预览到几天会练到哪些肌肉”。
- 用户给出的理由：不希望计划被固定动作模板限制。
- 未确认部分：分化轮换、日期安排及休息日插入的具体规则不得从 N 的数值自行推定。
- 适用规范：`training-programs`。

### D05：按实际健身房和器械安排动作

- 状态：已确认。
- 决定：记录健身房及其器械，动作候选结合实际器械，并提供肌肉图解、器械图片和使用方式。
- 确认依据：“锻炼能选择的动作要跟着器械走”“可以主动记录健身房及其器械，安排动作”。
- 用户给出的理由：选择动作时需要知道当前健身房有哪些器械，以及器械如何使用。
- 适用规范：`gym-equipment`、`exercise-stretch-library`。

### D06：保留原始重量单位和含义

- 状态：已确认。
- 决定：同一次训练允许不同器械使用 kg、lb，显示并保存原始数值；单只、单侧及总重量的含义不可静默改变。
- 确认依据：“健身房的器械的单位就是不一样的，换算显示只会可读性为0”；此前训练记录讨论要求按器械实际读数记录。
- 用户给出的理由：换算后的数值不便于训练现场读取和操作器械。
- 适用规范：`gym-equipment`、`training-data-access`。

### D07：拉伸与实际训练对应并提供选择

- 状态：已确认。
- 决定：训练和拉伸都提供教学及尽可能多个选择，根据所选训练动作匹配拉伸；按动作自身方式表达时长、次数和左右侧要求。
- 确认依据：“但是要包含拉伸的”“根据选择的训练动作自动匹配对应的拉伸”“训练和拉伸都应该尽可能提供多个选择”；此前拉伸讨论已明确不将全部动作统一为固定秒数。
- 用户给出的理由：现有软件不能完成对应拉伸安排。
- 适用规范：`exercise-stretch-library`。

### D08：统一风格且可替换的动作素材

- 状态：已确认。
- 决定：采用统一风格的插画或动画，优先免费素材，允许 Hevy 素材作为个人使用的临时补充；素材与动作身份分开，后续更换素材不破坏历史。
- 确认依据：此前素材讨论已确认上述偏好与补充方式；用户已说明私人使用范围。
- 未说明的理由：用户未给出指定最终素材库的决定，不将调研候选写成选定资料。
- 适用规范：`exercise-stretch-library`。最终素材收录与中文内容核验仍待执行。

### D09：自有后端和共享业务接口

- 状态：已确认。
- 决定：应用连接自己的后端同步数据；提供导入导出、开放接口，并开发通过同一套接口操作的 skill。
- 确认依据：“应用连接自己的后端同步数据”“要支持数据导入导出，并且有开放接口，设计一个skill可以直接通过同一套接口操作”。
- 用户给出的理由：训练前由助手安排计划，训练后助手直接读取实际记录进行分析。
- 边界：这里的操作 skill 是后续应用功能，不是已经安装的项目工程技能；当前没有宣称该操作 skill 已实现。
- 适用规范：`training-data-access`。

### D10：唯一 token 鉴权

- 状态：已确认。
- 决定：不设计账号密码，使用唯一 token 鉴权。
- 确认依据：“app不设计账号密码，使用唯一token鉴权”。
- 用户给出的理由：只供本人使用；没有确认多人账号体系。
- 适用规范：`training-data-access`。

### D11：官方 OpenSpec 与项目级工程技能

- 状态：已确认，项目接入已经执行。
- 决定：使用官方 OpenSpec；相关工程技能来自 `4o4E/skills` 的 `feat/openspec-decisions` 分支，安装在项目中，不全局安装 skill。
- 确认依据：用户指定 OpenSpec 与该分支，并进一步明确“我说的skill是安装到项目中而不是全局”。
- 实际接入：官方工作流程位于 `.omp/skills/openspec-*`；15 个工程技能的正文位于 `.agents/skills/`，分支来源记录在 `skills-lock.json`，`.omp/skills/` 的同名目录连接供当前助手读取。目录连接不是另一份技能正文。
- 工具范围：OpenSpec 命令行程序为全局工具；规范、官方项目技能及分支工程技能均在当前项目中。CLI 安装范围不等于 skill 安装范围。
- 用户未指定问题跟踪平台，不因接入工程技能而自动创建 GitHub 仓库、Issue 或其他平台配置。
- 适用规范：`project-workflow`。

## Risks / Trade-offs

- [安卓系统授权影响提醒] → 原生实现必须在真机验证日常切换应用和息屏，明确通知与定时唤醒权限，不以界面倒计时代替实际通知证明。
- [动作素材可能图文不符或缺少合适拉伸] → 收录时核验图示、中文说明、肌肉部位和器械条件；没有可行候选时如实说明，不假造覆盖范围。
- [器械数值含义在同步或分析时丢失] → 数据契约同时携带原始值、单位和必要的重量含义，导入导出验证这些语义。
- [计划被误当作已完成训练] → 计划与实际记录在业务接口中明确区分，以实际记录作为训练后分析依据。
- [后续改动素材破坏历史动作关联] → 保持动作身份独立于图片或动画的地址。

## Migration Plan

本次没有应用数据或数据库 schema 变更，没有部署和数据迁移。既有运动资料保持原样。后续如需迁移历史记录，先确认字段含义和迁移范围；数据库 schema 变更须获得用户确认后执行。
